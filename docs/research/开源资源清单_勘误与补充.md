# 开源资源清单：勘误与补充

**用途：** 对 `github资源.txt`（2025-08-11整理）的事实核查勘误，及新一轮真实开源项目补充
**核查日期：** 2026-08-11
**方法：** 逐条通过 WebSearch / web_fetch 实际验证仓库是否存在，不采信"看起来合理"的名称

## 一、勘误：原清单中的失实条目

原清单由LLM整理，**"王者荣耀专项"整节全部为虚构**，另有多条其他条目失实。使用原清单时请以此表为准：

| 原条目 | 判定 | 实际情况 |
|--------|------|----------|
| hok-framework (org) | ❌ 不存在 | 无此GitHub组织。腾讯真实仓库在 `tencent-ailab` 下（见第三节） |
| AiRobot-lab/King-of-Glory-AI-Challenge | ❌ 不存在 | 无此仓库。腾讯官方仓库是 `tencent-ailab/hok_env`、`tencent-ailab/hokoff`，但性质是强化学习训练环境，不是"竞赛方案集" |
| smoba-data-mining | ❌ 不存在 | 唯一相关的"smoba"仓库是营地签到/点赞机器人，与数据挖掘无关 |
| wzry-ai-coach | ❌ 不存在 | 不存在任何"AI教练"类的开源前例。最接近的是 `myBoris/wzry_ai`、`FengQuanLi/WZCQ`——这两个是**打游戏的操作机器人**（截屏+按键），不是赛后教练 |
| pbugnion/unity-ocr | ❌ 不存在，且方向性错误 | 王者荣耀并非Unity引擎（自研/Havok衍生引擎），即便该仓库存在，"同为Unity引擎适配性好"这个理由本身就不成立。**任何后续CV/OCR方案设计，不要假设Unity相关工具链适用** |
| google/bayes-irt | ❌ 不存在 | Google未发布此仓库 |
| vengle/awesome-ml-game-data | ❌ 不存在 | 无此清单 |
| LeagueSandbox/definitions | ❌ 路径错误，且组织已死 | 真实仓库名不同；该组织2022年收到Riot的律师函(C&D)，目前基本停滞，不建议参考 |
| adaptive-learning/awesome-adaptive-learning | ⚠️ 归属错误 | `adaptive-learning`组织存在（捷克研究项目，基本不活跃）但没有这个清单；真实清单是`realamirhe/awesome-adaptive-learning` |
| CAHLR/pyBKT | ✅ 真实，但适配性存疑 | 项目真实维护良好，但BKT专为"多学生+多技能"场景设计，单用户教练场景下是牵强适配，非天然契合 |

**其余条目**（YOLOv8、opendota、CLIP、Ultravox、CosyVoice、GPT-SoVITS、web-llm、Haystack、Langfuse、Ragas、Streamlit、Gradio、Dify、PostHog、openllmetry、shadcn/ui、xyflow、recharts）**均核实为真实且维护中**，rive-app/rive-renderer 已改名为 `rive-runtime`（同一项目，非虚构）。

### 对技术规格文档(tech spec)的影响
- **v1.0手动/半自动输入的选择被验证为正确**——不存在可直接套用的王者荣耀专项CV/OCR基础设施，`GameDataAdapter`的分层适配设计（手动→OCR→视频→官方API）没有捷径可抄，按当前节奏推进即可。
- **自适应学习那一节（pyBKT/bayes-irt）可以直接砍掉**，tech spec 4.2已经用规则函数`weekly_assessment()`实现了同样的效果，没必要引入外部依赖。
- v2.0若做CV部分，**不要套用Unity相关工具或假设**。

### 对PRD的影响
- 核心定位不用变，但"官方工具给数据，我们给判断"这个差异化论点被加强了：连开源社区都没人做出这个判断层，说明这确实是空白，不是重复造轮子。

## 二、补充：新一轮真实项目发现

分六个方向重新搜索，以下均逐一核实存在。置信度标注：✅高（已确认可访问/有真实star数）／⚠️中（有线索但未完全核实深度，需自行二次确认后再依赖）。

### 1. 王者荣耀专项工具
真实存在的只有**英雄元数据**类工具，**没有个人对局历史/API的替代品**——这一点和v1.0的核心风险假设完全吻合。

- `qing762/honor-of-kings-api`（✅ 22 stars）——抓取pvp.qq.com英雄数据（技能、胜率、克制关系），可作为教练点评时的英雄知识库/RAG语料，不涉及对局数据。
- `chg0901/Honor_of_Kings_Multi-modal_Dataset`（✅ 72 stars）——王者荣耀文本/图像/语音多模态数据集（英雄语音、背景故事），同样是游戏内容知识库，非对局数据。
- `tencent-ailab/hok_env`——除了RL训练环境外，**附带一个真实的官方回放解析工具（ABSTOOL.exe），可将`.abs`回放文件转成可视化视频**。这是目前唯一确认存在的"官方格式回放解析器"，值得纳入v2.0回放引擎的技术选型调研范围。

### 2. 同类MOBA教练工具（架构可借鉴）
这一类是本次搜索**最有价值的新发现**，几个项目的架构模式和本项目高度相似：

- **Aftermatch**（aftermatch-ai.com，闭源产品无仓库）——读取Riot对局timeline，用LLM对每次死亡指认具体归因（gank/换血亏/视野缺失/被迫开团），输出3个本局重点。**这是目前能找到的与本项目"决策点+反事实归因"设计最接近的真实案例**，虽然代码不开源，但报告结构值得研究参考。
- `BrightGir/dota-ai-coach`（✅ 25 stars，Go项目，活跃）——Dota2 GSI实时叠加层教练，RAG管道（BERT向量+Chroma向量库）检索英雄/装备知识库，LLM生成建议。是局内实时建议而非赛后复盘，但RAG-grounded教练架构可以直接参考。
- `sorena-ai/LeagueAiCoach`（⚠️中）——FastAPI服务，截图+语音提问输入，Whisper转写→LLM推理→TTS回复输出。这个语音进/语音出的教练循环架构和tech spec 4.3的语音对话流程几乎一致，值得看代码结构。
- League AI Coach（neohuman8.github.io/league-ai-coach，⚠️中）——用Riot官方Live Client + Match API做实时/赛后教练，走官方合规路径（不读内存）。合规架构参考价值高，但目前没有对应游戏的官方API可用，仅作设计参考。
- `whanyu1212/gem-dota`、`janjagusch/dota-2-ai-coach`（⚠️中，早期/单薄）——存在但成熟度低，仅作为"别人也在往这个方向摸索"的信号，不建议直接依赖代码。

### 3. 通用LLM赛事/游戏教练与归因框架
- 除上述Aftermatch外，**没有找到通用的"视频决策点提取+归因判断"开源框架**。这部分依然需要自建，属于本项目的核心技术壁垒，也是护城河所在。

### 4. MOBA小地图/HUD计算机视觉
- `maknee/League-ML-Minimap-Detection`（⚠️中，博客文档为主）——OpenCV的LoL小地图英雄头像检测+阵营区分，是目前少见的真实小地图CV前例，但LoL专属、非正式仓库形态，需要自行验证博客对应代码的可用性。
- `kenneth-ew/MOBA-Minimap-Awareness-Trainer`（✅ 33 stars）——眼动追踪的小地图意识训练器，是"训练玩家看小地图"而非"AI识别小地图"，用途不同但UI标注小地图区域的方式可参考。
- **击杀播报OCR方向完全空白**——没有找到任何MOBA击杀信息OCR的开源实现。这部分tech spec里标注为v2.0技术债务是合理的，实际开发时预期要从通用OCR引擎（如PaddleOCR）自己训练/适配，没有现成方案。

### 5. 语音反思式教练框架（非游戏领域，架构可迁移）
- `Ender00420/Reflecting-in-the-Reflection`（对应论文 arXiv 2601.14798）——双Agent苏格拉底式提问框架，一个"教师"agent诊断薄弱点并追问反思。**这是目前找到的与"你当时在想什么"这套对话逻辑最贴近的架构**，建议复盘引擎的提示词设计时参考其双agent分工方式。
- `shreyastaware/ai_fitness_coach`（⚠️中）——电话语音健身教练，维护对话上下文，语音通话的工程管路可参考。

### 6. 王者荣耀公开对局数据集
- 没有找到任何Kaggle/HuggingFace上的王者荣耀个人对局数据集。
- `tencent-ailab/hokoff`——真实存在的对局日志，但用于离线RL训练，只能作为**统计意义上的参照基线**（比如平均胜率曲线），不能替代个人对局历史。
- **结论：官方API和替代数据集都不存在，v1.0手动打卡+截图OCR仍是唯一可行路径**，这与PRD的风险应对章节完全吻合，无需改变策略。

## 三、对项目的实际行动建议

1. **不改变v1.0技术路线**——原tech spec的手动优先策略被两轮验证证明是唯一现实选项，不是保守，是没有更好的路。
2. **删除pyBKT/bayes-irt依赖计划**，规则引擎已经够用。
3. **调研`tencent-ailab/hok_env`的ABSTOOL回放解析器**，看能否解析出比手动标记更结构化的原始数据，作为v2.0自动化的候选起点。
4. **复盘引擎提示词设计时参考`Reflecting-in-the-Reflection`的双agent苏格拉底提问模式**，可能比单一prompt模板更能还原"问你当时在想什么"的效果。
5. **Aftermatch的归因报告结构值得直接借鉴格式**（即使代码不开源），作为"这波到底是谁的问题"报告模板的参考对象。
6. 标记为⚠️中置信度的仓库（sorena-ai/LeagueAiCoach、maknee的小地图检测博客等）在正式引用前需要自己再次打开链接确认代码可用，本文档不保证其当前可访问性。
