# Q3: Few-shot/Zero-shot Icon Matching — Newer Methods

## Directly related research

所有条目均已通过抓取一级来源页面（arXiv abs 页）核实标题、作者、年份与摘要。

### 1. XFeat: Accelerated Features for Lightweight Image Matching
- **Authors**: Guilherme Potje, Felipe Cadar, Andre Araujo, Renato Martins, Erickson R. Nascimento
- **Year / Venue**: 2024 / CVPR 2024, arXiv:2404.19174
- **URL**: https://arxiv.org/abs/2404.19174
- **Task / dataset**: 局部特征检测+描述+匹配（sparse 与 semi-dense 两种模式），评测于 pose estimation 与 visual localization 基准。作者强调"面向资源受限设备的快速鲁棒算法"，并展示在**普通笔记本 CPU 上实时运行**、比现有深度局部特征快最多 5×（[arXiv abs](https://arxiv.org/abs/2404.19174)）。
- **Relevance**: **direct** — 可直接替代 cv2.matchTemplate 的匹配核心：把固定 UI 图标当作模板图，用 XFeat 描述子做对应点匹配 + 几何验证，天然对缩放、分辨率变化、轻微遮挡与半透明叠加更鲁棒。
- **Migration assessment**: 零标注（预训练权重直接用，无需游戏内数据微调），推理开销为轻量 CNN 级别，作者自证 CPU 实时，因此手机端可行；工程上需要自己加 mutual-nearest-neighbor + RANSAC/单应验证来判"是否命中"，比 matchTemplate 多一层后处理逻辑。

### 2. LightGlue: Local Feature Matching at Light Speed
- **Authors**: Philipp Lindenberger, Paul-Edouard Sarlin, Marc Pollefeys
- **Year / Venue**: 2023 / arXiv:2306.13643（页面未标注会议；社区通行为 ICCV 2023，此处仅按已核实页面陈述）
- **URL**: https://arxiv.org/abs/2306.13643
- **Task / dataset**: 稀疏局部特征匹配器（SuperGlue 的高效重设计），显存与算力都更省，且**推理时间随匹配难度自适应**——重叠大、外观变化小的图像对推理更快（[arXiv abs](https://arxiv.org/abs/2306.13643)）。
- **Relevance**: **direct** — UI 图标匹配正属于"容易的图像对"（同一渲染源、无视角变化），自适应早停会让实际耗时远低于最坏情况。
- **Migration assessment**: 免标注、免微调；需搭配关键点提取器（SuperPoint 或上面的 XFeat）。原始实现偏 GPU 友好，落到手机需 ONNX/CoreML/NCNN 导出与量化；对纯图标小图 patch，模型可能属于"过度设计"，建议作为精度上限基线而非首选端侧方案。

### 3. Efficient LoFTR: Semi-Dense Local Feature Matching with Sparse-Like Speed
- **Authors**: Yifan Wang, Xingyi He, Sida Peng, Dongli Tan, Xiaowei Zhou
- **Year / Venue**: 2024 / CVPR 2024, arXiv:2403.04765
- **URL**: https://arxiv.org/abs/2403.04765
- **Task / dataset**: detector-free 半稠密匹配；提出带自适应 token 选择的聚合注意力与两级相关层，比 LoFTR 快约 2.5×，甚至超过 SuperPoint+LightGlue 流水线（[arXiv abs](https://arxiv.org/abs/2403.04765)）。
- **Relevance**: **transferable** — detector-free 特性对**低纹理**目标（纯色按钮、扁平图标、数字血条底板）尤其有价值，这正是 SIFT/ORB 类关键点最容易失效的场景。
- **Migration assessment**: 依然是 Transformer 主干，参数与显存高于 XFeat，作者未给移动端数据；建议只在"模板匹配置信度低"的困难帧上作为兜底二级匹配调用，而非逐帧全量跑。

### 4. MobileCLIP: Fast Image-Text Models through Multi-Modal Reinforced Training
- **Authors**: Pavan Kumar Anasosalu Vasu, Hadi Pouransari, Fartash Faghri, Raviteja Vemulapalli, Oncel Tuzel
- **Year / Venue**: 2023（v2 2024）/ CVPR 2024, arXiv:2311.17049
- **URL**: https://arxiv.org/abs/2311.17049
- **Task / dataset**: 面向**移动端运行时**优化的图文对比模型族，用多模态强化训练（caption 模型 + CLIP 教师集成的知识迁移）提升小模型精度；MobileCLIP-S2 比 ViT-B/16 版 CLIP 快 2.3× 且更准，在零样本分类与检索上刷新 latency-accuracy 前沿（[arXiv abs](https://arxiv.org/abs/2311.17049)）。
- **Relevance**: **transferable** — 提供手机可跑的通用视觉嵌入：把每个固定图标的 1–5 张样例编码成 prototype 向量，线上用余弦相似度做最近邻/度量学习式识别（即 few-shot 原型网络的低成本实现），也支持文本零样本兜底。
- **Migration assessment**: 无需训练，仅需每类几张样例算 prototype；图像编码器有官方移动端友好变体，可量化后端侧部署。缺点是全局嵌入对"图标在屏幕何处"无定位能力，需先用固定 ROI 裁切（我们场景 UI 位置固定，正好满足）。

### 5. GUing: A Mobile GUI Search Engine using a Vision-Language Model
- **Authors**: Jialiang Wei, Anne-Lise Courbis, Thomas Lambolais, Binbin Xu, Pierre Louis Bernard, Gérard Dray, Walid Maalej
- **Year / Venue**: 2024 / ACM TOSEM（页面标注 accepted），arXiv:2405.00145
- **URL**: https://arxiv.org/abs/2405.00145
- **Task / dataset**: 训练 GUI 领域专用视觉语言模型 GUIClip，并公开 303k 应用截图（其中 135k 带 caption）数据集，用于文本→GUI 截图检索（[arXiv abs](https://arxiv.org/abs/2405.00145)）。
- **Relevance**: **adjacent** — 不是 few-shot 图标匹配方法，但证明了"在 GUI/截图域上继续对比预训练，可显著优于通用 CLIP"这条路线，并给出可复用的截图语料。
- **Migration assessment**: 直接用于我们的图标识别偏重；价值在于提供"域内自监督/弱监督预训练 + 小样本原型分类"的可行范式与预训练权重来源。自行按此范式在王者荣耀截图上做轻量对比预训练成本中等（需批量无标注截图，标签几乎不需要）。

### 其他已核实的备选（同为 2022+，可按需深入）
- OmniGlue: Generalizable Feature Matching with Foundation Model Guidance，Hanwen Jiang 等，CVPR 2024，https://arxiv.org/abs/2405.12979 —— 以基础模型知识引导匹配，专攻**未见域**泛化（对不同机型/分辨率/皮肤外观变化的跨域鲁棒性有直接意义），但计算量高于 XFeat。
- JamMa: Ultra-lightweight Local Feature Matching with Joint Mamba，Xiaoyong Lu, Songlin Du，CVPR 2025，https://arxiv.org/abs/2503.03437 —— Mamba 线性复杂度匹配器，参数与 FLOPs 不到注意力类匹配器的 50%。

# Q7: Lightweight On-device Deployment

## Directly related research

### 1. MobileOne: An Improved One millisecond Mobile Backbone
- **Authors**: Pavan Kumar Anasosalu Vasu, James Gabriel, Jeff Zhu, Oncel Tuzel, Anurag Ranjan
- **Year / Venue**: 2022（v2 2023）/ CVPR 2023, arXiv:2206.04040
- **URL**: https://arxiv.org/abs/2206.04040
- **Task / dataset**: 分类/检测/分割；核心论点是 FLOPs 与参数量与真实手机延迟相关性差，因此**直接以设备延迟为优化目标**做结构设计与训练时重参数化；变体在 iPhone12 上推理 <1 ms，ImageNet top-1 75.9%（[arXiv abs](https://arxiv.org/abs/2206.04040)）。
- **Relevance**: **direct** — 若我们要把图标/状态识别换成学习式小分类器或检测头，MobileOne 是最直接的骨干选择，其"以实测延迟为准"的方法论也应直接搬进我们的选型流程。
- **Migration assessment**: 需要少量标注（每类几十张即可，配合数据增广/模板合成可自动生成）；训练后重参数化为纯推理结构，端侧部署简单，延迟预算极小。

### 2. FastViT: A Fast Hybrid Vision Transformer using Structural Reparameterization
- **Authors**: Pavan Kumar Anasosalu Vasu, James Gabriel, Jeff Zhu, Oncel Tuzel, Anurag Ranjan
- **Year / Venue**: 2023 / ICCV 2023, arXiv:2303.14189
- **URL**: https://arxiv.org/abs/2303.14189
- **Task / dataset**: 混合 ViT，提出 RepMixer token 混合算子降低内存访问成本；同精度下在移动端比 EfficientNet 快 4.9×、比 ConvNeXt 快 1.9×，同延迟下比 MobileOne 高 4.2% top-1，并强调对**分布外样本与图像损坏更鲁棒**（[arXiv abs](https://arxiv.org/abs/2303.14189)）。
- **Relevance**: **direct** — 鲁棒性 + 移动延迟双优，适合应对录屏压缩伪影、不同机型渲染差异。
- **Migration assessment**: 与 MobileOne 同一套工程链路（Apple 官方开源、有 CoreML 导出），标注需求与部署成本相当；建议作为 MobileOne 的精度更高档位备选。

### 3. Efficient Track Anything (EfficientTAM)
- **Authors**: Yunyang Xiong, Chong Zhou, Xiaoyu Xiang, Lemeng Wu, Chenchen Zhu, Zechun Liu, Saksham Suri, Balakrishnan Varadarajan, Ramya Akula, Forrest Iandola, Raghuraman Krishnamoorthi, Bilge Soran, Vikas Chandra
- **Year / Venue**: 2024 / arXiv:2411.18933（页面未标注会议）
- **URL**: https://arxiv.org/abs/2411.18933
- **Task / dataset**: 轻量化 SAM 2：用非层级的 plain ViT 作图像编码器 + 高效记忆模块，在 semi-supervised VOS 与 promptable video segmentation 上与 SAM 2 (HieraB+) 相当，A100 上约 2× 加速、参数约 2.4× 缩减，明确以"手机端视频目标分割"为动机（[arXiv abs](https://arxiv.org/abs/2411.18933)）。
- **Relevance**: **transferable** — 若后续需要跟踪非固定元素（英雄头像位移、技能特效区域、小地图目标），这是端侧可行的视频分割/跟踪方案。
- **Migration assessment**: 零标注（prompt 驱动），但即便"高效版"仍显著重于图标匹配需求，手机实时需进一步量化与降分辨率；对当前固定 UI 任务属于备用能力，不建议作为主链路。

### 4. FrameHopper: Selective Processing of Video Frames in Detection-driven Real-Time Video Analytics
- **Authors**: Md Adnan Arefeen, Sumaiya Tabassum Nimi, Md Yusuf Sarwar Uddin
- **Year / Venue**: 2022 / DCOSS 2022, arXiv:2203.11493
- **URL**: https://arxiv.org/abs/2203.11493
- **Task / dataset**: 边缘-云协同视频分析；把"跳过多少连续帧"建模为误差 vs 处理率优化问题，用离线强化学习学出 skip-length 策略，在摄像端跑一个轻量 RL agent 过滤帧，只把选中帧交给检测器（[arXiv abs](https://arxiv.org/abs/2203.11493)）。
- **Relevance**: **direct** — 对录屏分析性价比最高的一类优化：MOBA 录屏中绝大多数相邻帧的 UI 区域完全不变，学习式/启发式跳帧能把有效计算量降一个数量级。
- **Migration assessment**: 无需视觉标注（用检测输出一致性作为奖励信号自监督地学策略），额外算力接近零；最容易在现有 cv2 流水线上落地的一步，且与换不换匹配模型无关。

### 5. Computation-efficient Deep Learning for Computer Vision: A Survey
- **Authors**: Yulin Wang, Yizeng Han, Chaofei Wang, Shiji Song, Qi Tian, Gao Huang
- **Year / Venue**: 2023 / arXiv:2308.13998（页面未标注会议）
- **URL**: https://arxiv.org/abs/2308.13998
- **Task / dataset**: 综述，覆盖四条主线：静态/动态轻量骨干、任务专用高效架构与算法、模型压缩技术、硬件平台部署策略，并讨论"实际效率"与更现实的压缩评估（[arXiv abs](https://arxiv.org/abs/2308.13998)）。
- **Relevance**: **transferable** — 作为端侧优化的技术地图：蒸馏、剪枝、量化、动态推理（early-exit / 分辨率自适应）如何组合选型。
- **Migration assessment**: 无迁移成本，是路线图而非方法；建议按其"实际效率而非 FLOPs"的评估建议来定我们的端侧验收指标。

### 其他已核实的备选
- GEMEL: Model Merging for Memory-Efficient, Real-Time Video Analytics at the Edge，Arthi Padmanabhan 等，2022，https://arxiv.org/abs/2201.07705 —— 通过共享相似模型层降低边缘显存最多 60.7%，适合我们同时跑多个识别模型的场景。
- EdgeMA: Model Adaptation System for Real-Time Video Analytics on Edge Devices，Liang Wang 等，ICONIP 2023，https://arxiv.org/abs/2308.08717 —— 检测域漂移（版本更新、皮肤/UI 改版）并做重要性加权的在线模型自适应。

## Conclusion

Q3 有成熟且可直接落地的替代路径：以 XFeat 这类"为 CPU/端侧设计的学习式局部特征"替换 cv2.matchTemplate 的相似度核心，配合 MobileCLIP 原型向量做每类 1–5 样本的度量学习式判别，两者都**无需标注、无需训练**，鲁棒性和跨机型/分辨率泛化明显优于模板匹配与感知哈希。Q7 的学术共识是"以实测设备延迟而非 FLOPs 为优化目标"（MobileOne/FastViT）并叠加系统层的冗余削减（FrameHopper 的学习式跳帧、GEMEL 的模型合并），其中跳帧对录屏这种高时序冗余数据收益最大且改动最小。整体建议顺序：先上跳帧与 ROI 裁切降算力，再用 XFeat/MobileCLIP 替换匹配核心，仅在困难帧兜底调用 Efficient LoFTR，暂不引入 EfficientTAM 级别的视频分割模型。
